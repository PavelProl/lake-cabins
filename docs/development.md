# Процесс разработки project-grove

Обязательные границы — в [AGENTS.md](../AGENTS.md). Разделы ниже читаются по его условиям.

## Начало и продолжение работы

При наличии .local/STATE.md прочитай активную задачу и состояние оттуда, затем нужные
требования брифа. Публичный [план](PLAN.md) содержит только технические задачи,
не личный контекст и не выданные разрешения. Если локального файла нет, восстанови
задачу и разрешения из текущего чата, уточняя только недостающее; не считай отсутствие
записи разрешением. README читай для команд, демо и ограничений. Если задача ведётся в Issue,
прочитай описание, комментарии и связанные PR с результатами и ограничениями.
При недоступности источника обозначь неопределённость до зависимых действий.

Сверь ветку, HEAD, git status, staged/unstaged diff и относящиеся untracked-файлы.
Не повторяй проверки только ради восстановления контекста. При расхождении
сначала восстанови факты; код не доказывает принятие требования, статус не даёт разрешения.
Сообщения «продолжаем работу» достаточно в известной папке; специальная передача необязательна.

Локальные материалы `Фото домиков/`, `CLAUDE.md`, `docs/owner-questions.md`,
`docs/research-2026-10.md`, `docs/retrospective-2026-11.md`, `output/` и исходники
сохраняй вне Git: не добавляй, не удаляй и не меняй автоматически.
В задачу могут входить отдельно выбранные копии фото в `src/assets`.

## Задачи и проверки

Выбирай проверки по риску и критериям задачи: текст — содержание, ссылки и diff;
поведение — подходящие автоматические и браузерные проверки.
Для ошибки сначала получи воспроизведение. Начинай с дешёвых полезных проверок.
После исправлений повторяй затронутые; полный набор — при широком риске или условии выпуска,
не только из-за commit, push или merge. Для визуальных правок заранее определи показ разработчику.

Привязывай результат к проверенной версии. Различай выполненное и предполагаемое,
чтение кода и запуск, эмуляцию и реальное устройство; называй недоступные проверки.
Не добавляй тесты, зависимости и инфраструктуру ради формальной полноты.
Читай целевой контекст, группируй независимые проверки и давай короткие итоги вместо успешных логов.

## Цикл задачи и агентное ревью

1. Согласуй результат, границы, критерии и ограничения, если это ещё не сделано.
   Деление — на законченные проверяемые результаты с реальными зависимостями,
   а не слои «компоненты / стили / тесты». Issue не обязательна.
2. Зафиксируй исходный SHA и согласованный состав изменений, сохрани постороннюю работу.
   Обычно задача соответствует ветке и PR; соблюдай явно заданный разработчиком порядок.
3. Выполни задачу и подходящие проверки. Обычные шаги утверждённой задачи не пересогласовывай.
4. Передай отдельному read-only ревьюеру базовый SHA, критерии или Issue, инструкции,
   версию контекста, полный diff, новые untracked-файлы и результаты проверок.
   Он самостоятельно читает затронутые файлы и проверяет дефекты и соответствие задаче.
5. Замечание содержит важность, место, сценарий, последствие и основание.
   Предпочтения отделяются от дефектов. При отсутствии замечаний укажи объём и ограничения.
   Исполнитель исправляет подтверждённое либо объясняет отклонение; тот же ревьюер
   проверяет исправления и влияние. Неизменившееся полностью не перечитывается.
   Повторяющийся спор и новый значимый выбор вынеси разработчику.
6. После устранения блокирующих дефектов покажи пакет приёмки по AGENTS.
   Нерешённые существенные проблемы называй явно; новые требования согласуй отдельно.
   Git и внешние действия выполняй только при явном разрешении.

Одна активная задача, один исполнитель и один ревьюер по умолчанию.
Отдельный тестировщик и диспетчер не нужны. Для анализа без изменений ревью необязательно.
Мелкие исправления входят в текущую задачу, а не отдельные Issues.
Агентное ревью не является GitHub approval независимого человека.

## Координация агентов

Один координатор ведёт рабочее состояние в .local/STATE.md и утверждённые требования.
Несколько исполнителей применяются при конкретной пользе в согласованных границах.
Разделяй задания по результату и файлам; пересечения выполняй последовательно
либо изолируй с явным порядком интеграции.

Передавай агенту задачу, критерии, исходный SHA, версию контекста, незакоммиченный контекст,
границы файлов, разрешения, процедуру и её версию, модель и усилие.
При изменении требований, критериев, границ и общих процедур обнови основной документ,
повышай версию контекста, уведомляй затронутых агентов и проверяй применимость их работы.
Перед сдачей и интеграцией сверяй актуальность и реальные изменения: SHA и номера недостаточно.
Конфликтующий результат не интегрируй до согласования решения.

## Смена чата и задачи

Меняй чат, когда накопленный контекст мешает работе; фиксированного лимита сообщений нет.
Перед завершением этапа, сменой задачи или передачей сопоставь следующий шаг с общей целью
и незавершёнными договорённостями. Сам предложи необходимую подготовку и недостающие решения;
не перекладывай поиск связей между этапами на разработчика.

Сохрани требования в брифе, рабочее состояние и разрешения в .local/STATE.md.
Статус публичной Issue обновляй без личного контекста и только при разрешении.
Локальное состояние обновляется после согласования, существенного решения, проверки и перед ожиданием пользователя.
Храни снимок состояния, не дневник. В передаче достаточно задачи, ветки/SHA, незавершённого,
проверок, следующего шага и разрешений; постоянные правила не переписывай.

При внезапном закрытии последнее действие может быть не записано — восстанови факты.
Чат с доступом только к GitHub не видит локальное состояние. Передавай необходимые
закрытые сведения только напрямую в нужный чат; не публикуй их ради передачи контекста.

## Git и GitHub

Перед действием проверь его явное разрешение и границы. Приёмка результата не даёт
автоматического разрешения на commit, push, Issues, PR, merge или публикацию.
Несколько действий можно разрешить одной фразой; уже разрешённое повторно не согласовывай.
Без разрешения сохрани состояние в .local/STATE.md и остановись на соответствующем шаге.
Локальная передача в новый чат возможна без коммита; это не завершение задачи.

Перед commit проверь индекс и рабочее дерево. Проверь смысл всего публикуемого diff:
нет ли личных целей, переписки, выданных разрешений, служебных отчётов и локальных путей.
Проверь, что .local/STATE.md игнорируется и не отслеживается; не добавляй его принудительно.
Добавляй только утверждённые файлы,
сверь staged diff с принятым результатом. При расхождении остановись и сообщи.
Commit message: `<type>: <action summary>`, на английском;
типы: docs, feat, fix, refactor, test, chore.

Issues описывают результат, критерии и реальные зависимости; публикация и изменения согласуются.
PR описывает итоговое поведение, проверки, итог ревью и ограничения, на русском.
Для описания PR применяй доступный skill `pr` в рамках разрешений.
Если задача в Issue — укажи `Closes #<issue>`; при изменении объёма обнови PR.
После новых изменений проверь их перед merge. Не обходи обязательные проверки GitHub.
Issue закрывается после merge связанного PR, не после локальной реализации.

## Skills

Обязательных внешних skills нет. Базовые процедуры этого документа работают без них;
skill не расширяет разрешений и не хранит единственную копию состояния.
Сначала оцени готовое решение: использовать, адаптировать, создать своё при конкретном
пробеле либо обойтись без skill.

До подключения прочитай SKILL.md и необходимые ресурсы. Проверь источник, версию/SHA,
лицензию, инструменты и доступность, запись файлов и команды, подагентов, внешние действия,
стоимость, совместимость с правилами и допустимую замену.
Для выбранного решения зафиксируй в .local/STATE.md источник, версию, изменения, применение,
ограничения и замену. Одноимённые skills не считай одинаковыми; происхождение не угадывай.
Обновления принимай отдельно от активной задачи; весь каталог заранее не устанавливай.
При отсутствии необязательного skill назови базовую замену, обязательного — сообщи о блокировке.

## Модели и усилие

Устойчивая политика — здесь; выбор и разрешённые настройки текущей задачи — в .local/STATE.md.
Изменчивые характеристики проверяй по официальным источникам, доступность — в рабочей среде.
Оцени сложность, неопределённость, цену ошибки, проверяемость, стоимость и скорость.
Сначала необходимое качество, затем стоимость принятого результата с переделками и подагентами.

Ясная локальная правка допускает экономную настройку; требования, планирование,
реализация и ревью обычно требуют основной модели и среднего усилия.
Недостающие факты сначала получай. Повышай усилие для сложного рассуждения;
меняй модель при ограничениях возможностей или устойчивого качества.
После двух содержательных попыток без прогресса пересмотри гипотезы и контекст,
затем предложи другой подход или настройку. Максимальное усилие требует обоснованной пользы.
Снижать настройку разумно на самостоятельной подзадаче после снятия неопределённости.
Усилия разных моделей не эквивалентны; API-цена не определяет расход подписочного лимита.

Основную настройку предлагает агент и согласует на естественной остановке;
автоматического переключения не обещай. Не останавливайся ради переключения перед обычным Git.
Координатор выбирает подагентов внутри согласованных границ и сообщает выбор;
выход за границы и отсутствие разрешённой замены согласуются отдельно.

## Документация и решения

| Место | Основное назначение |
|---|---|
| README.md | Представление, запуск, проверки, демо и ограничения |
| docs/project-brief.md | Требования, визуальное направление и продуктовые вопросы |
| docs/PLAN.md | Только технические задачи и этапы продукта |
| .local/STATE.md (вне Git) | Текущая задача, продолжение, разрешения, проверки и настройки агента |
| AGENTS.md | Обязательные правила и условия чтения процедур |
| docs/development.md | Подробные процедуры по необходимости |
| Issues / PR | Утверждённая задача в трекере / ревью и результат реализации |

Если задача в Issue, локальное состояние содержит ссылку и продолжение без второго описания и статуса.
Состояние обновляй локально; согласованные требования к продукту — в брифе.
Личные цели и история общения не нужны в публичной документации.
Закрытое состояние храни минимальным: только сведения, необходимые для продолжения.
Оно не является публичным отчётом и не переносится автоматически в Issues или PR.
Новые документы и существенную перестройку согласуй. Предложения отмечай явно;
локальные исследовательские заметки не становятся требованиями автоматически.

Не переноси инструкции playbook механически и не создавай вложенные AGENTS без локальной специфики.
Основа адаптации: project-playbook 0.1; обязательных ссылок на соседнюю папку нет.
ADR нужен после согласования значимого выбора с дорогой сменой и реальными альтернативами:
контекст, альтернативы, решение, последствия, статус. Папку заранее не создавай.
После нескольких задач или существенного этапа проверь актуальность затронутых документов,
без полного перечитывания после каждой правки и без отдельного журнала проверок.

## Улучшение по результатам ошибок

Перед изменениями, внешними действиями и отчётом сверяй задачу, разрешения и состав файлов.
При отступлении останови зависимые действия, назови ошибку и исправь разрешённое.
Установи причину, выбери минимальную меру против повторения и проверь результат.
Нужное новое правило или документ сначала согласуй; храни его в основном месте без дублирования.
Не исправляй процесс неразрешённым commit, push или изменением чужой работы.
Ретроспектива нужна по запросу или после существенного сбоя, не после каждой мелочи.
